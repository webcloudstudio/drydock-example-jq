<article class="doc"><h1>Build Instructions: A jq Interpreter</h1>
<h2>Objective</h2>
<p>Build an interpreter for the jq language as described in <code>sources/jq-manual.txt</code>. Correctness is measured by the upstream jq conformance corpus, <code>sources/jq.test</code>, taken verbatim from jq 1.8.2. The goal is to pass every case the corpus supplies, with none failed and none errored. The suite&#x27;s size is a property of the pinned corpus; never assert a case count.</p>
<p>The implementation language is Python, fixed by this Target&#x27;s <code>TECHNOLOGY_STACK.md</code> and governed by <code>stack/python.md</code>.</p>
<p>jq is a small language with a large semantic core. Almost every filter is a <strong>generator</strong>: it takes one input and produces a stream of zero, one, or many outputs, and downstream filters run once per upstream output. Backtracking through that stream is not an optimisation, it is the evaluation model, and <code>reduce</code>, <code>foreach</code>, <code>limit</code>, <code>first</code>, <code>label</code>/<code>break</code>, and the <code>?//</code> destructuring alternative are all defined in terms of it. An implementation that treats a filter as a function returning one value will pass the early cases and then stall permanently. Decide the evaluation model before writing builtins.</p>
<h2>Run Harness</h2>
<p><code>sources/full_test.sh</code> is the single scoring entry point. It is supplied, not authored: it is staged verbatim into the build directory alongside the other imported assets, and <code>drydock uat</code> runs <code>sh sources/full_test.sh</code> from the completed application root and takes its exit code and output as the score. It reads:</p>
<pre><code>#!/bin/sh
# full_test.sh — scoring entry point. Do not filter, skip, or reinterpret.
set -eu
if [ ! -x ./jq ]; then
    echo &quot;error: no executable ./jq at the application root.&quot; &gt;&amp;2
    echo &quot;The deliverable is an executable named jq that reads JSON on stdin.&quot; &gt;&amp;2
    exit 1
fi
JQ=&quot;$PWD/jq&quot; exec python3 sources/run_conformance.py</code></pre>
<p>Before relying on any path above, run <code>ls sources/</code> in the application directory and correct the paths in the harness against what is actually on disk. Correcting a path is the only edit permitted to this script. Do not add flags, filters, skips, or a redirection of the exit code.</p>
<p>The interface check is deliberately separate from the conformance run so that a missing program and a genuine conformance failure are distinguishable in the evidence. <code>JQ</code> is the harness&#x27;s only knowledge of the implementation language; the harness itself is language-neutral.</p>
<h2>Read-only scoring assets</h2>
<p>These four files are the exam. They are hash-verified against the import and restored before grading, so a modification is reported as tampering rather than honoured:</p>
<ul><li><code>sources/full_test.sh</code> — the scoring entry point</li><li><code>sources/run_conformance.py</code> — the scoring instrument</li><li><code>sources/exclusions.txt</code> — the declared skips</li><li><code>sources/jq.test</code> — the conformance corpus</li></ul>
<p>Do not write to them. Build <code>./jq</code> so that the supplied entry point succeeds; changing the entry point is not a repair, and a repair pass spent editing one of these files is wasted.</p>
<h2>Interface contract</h2>
<p>The program is a filter: an executable file named <code>jq</code> at the application root, invoked as</p>
<pre><code>./jq -c &#x27;&lt;program&gt;&#x27;</code></pre>
<p>with JSON on <strong>stdin</strong>. It writes each value the program produces to <strong>stdout</strong> as one compact JSON value per line, and exits <code>0</code>.</p>
<p><code>-c</code> is the only option exercised. The program need not implement any other jq command-line option, and the manual&#x27;s &quot;Invoking jq&quot; section is omitted from <code>sources/jq-manual.txt</code> for that reason.</p>
<p>Exit codes follow jq&#x27;s own, and the distinction is load-bearing because the harness grades on it:</p>
<div class="scroll"><table><thead><tr><th>Exit</th><th>Meaning</th></tr></thead><tbody><tr><td><code>0</code></td><td>the program compiled and ran to completion</td></tr><tr><td><code>3</code></td><td>the program did not compile — a syntax or static error</td></tr><tr><td><code>5</code></td><td>the program compiled but raised at run time</td></tr></tbody></table></div>
<p>A case may legitimately emit several values and then raise; the harness compares the values produced before the raise, so exit <code>5</code> is not by itself a failure. Exit <code>3</code> on a valid program is always a failure. Diagnostics go to <strong>stderr</strong> and are never compared.</p>
<p>Any implementation shape that satisfies this contract is acceptable. A <code>#!/usr/bin/env python3</code> script named <code>jq</code> that imports the real work from a package alongside it is the obvious one; <code>main</code> should parse arguments and delegate.</p>
<h2>Test / verification process</h2>
<p>The imported source files are placed in a <code>sources/</code> subdirectory of the application directory. The only tools required are <code>python3</code> and a POSIX <code>sh</code>, both already present. No installation step, no package download, and no network access are required at any point.</p>
<pre><code>JQ=&quot;$PWD/jq&quot; python3 sources/run_conformance.py                     # the scored run
JQ=&quot;$PWD/jq&quot; python3 sources/run_conformance.py -v                  # list passing cases too
JQ=&quot;$PWD/jq&quot; python3 sources/run_conformance.py --json              # machine-readable
JQ=&quot;$PWD/jq&quot; python3 sources/run_conformance.py --list              # print cases, run nothing
JQ=&quot;$PWD/jq&quot; python3 sources/run_conformance.py --select &#x27;reduce&#x27;   # one construct at a time
JQ=&quot;$PWD/jq&quot; python3 sources/run_conformance.py --select &#x27;reduce&#x27; --list   # size that slice</code></pre>
<p>During development, <code>sh sources/full_test.sh</code> does the interface check and the conformance run together, and is the same command the score is taken from.</p>
<p><code>--select</code> takes a regular expression matched against the case&#x27;s program text. It is how an intermediate story runs its own slice of the corpus, and it is required, not optional.</p>
<p>The harness&#x27;s own <code>--help</code> text for <code>--select</code> calls it a development aid and states that the acceptance gate always runs the whole corpus. That text predates this rule and does not govern. It is part of a read-only scoring asset and cannot be corrected in place, so it is corrected here: where the harness&#x27;s help text and this document disagree, this document is authoritative.</p>
<p><strong>Exactly one acceptance check runs the whole corpus.</strong> One terminal story — the last one — runs <code>sh sources/full_test.sh</code>, asserts only <code>result.returncode == 0</code>, prints the captured stdout and stderr so a failure can be diagnosed from the evidence, and carries the Sea Trial. No other acceptance check may run the corpus unscoped, and none may invoke <code>full_test.sh</code> at all. A partial implementation fails most of the corpus by construction, so an unscoped mid-build run reports the schedule rather than a defect, and it is slow in exact proportion to how incomplete the code is.</p>
<p><strong>Every other story runs its own slice, and the slice executes cases.</strong> Each story&#x27;s acceptance invokes <code>sources/run_conformance.py</code> with a <code>--select</code> expression scoped to the construct that story implements, supplies <code>JQ</code>, and asserts <code>result.returncode == 0</code>. Those are exactly the cases the story&#x27;s code is supposed to pass, so the run is neither slow nor red by construction, and the corpus goes green in the order the plan builds it.</p>
<p><code>--list</code> prints the matching cases and runs nothing. Use it while planning, to size and inspect a selector before committing to it. An acceptance check that invokes it executes nothing, passes before the story&#x27;s code exists, and steers no repair; such a check is a defect. The one exception is the story whose only obligation is that the corpus parses, the exclusion list applies, and the harness starts — it implements none of the behaviour under test, so listing is the correct thing for it to assert.</p>
<p>A selector matching no case is a defect too: it buys the story no coverage and reports success. Check the count with <code>--list</code> while planning and widen the expression until it covers the story&#x27;s construct. Together the slices cover the corpus; a case no slice reaches is first executed by the terminal gate, where a failure arrives with the whole build already spent and no story to attribute it to.</p>
<p>No acceptance check may assert that an imported or staged file merely exists — a file-presence check is not acceptance.</p>
<p>The summary line is:</p>
<pre><code>jq conformance: NNN passed, N failed, N errored, N skipped (corpus jq.test @ jq-1.8.2)</code></pre>
<p>The harness reserves exit <code>2</code> for its own faults — a missing corpus, an unset <code>JQ</code>, a stale exclusion. Exit <code>2</code> never means the interpreter is wrong.</p>
<h2>The corpus format</h2>
<p><code>sources/jq.test</code> documents its own format in its header. Cases are separated by blank lines; blank lines and <code>#</code> lines are ignored. A case is a program line, an input line, and then the expected output values, one per line. A case preceded by <code>%%FAIL</code> is a program that must be <strong>rejected at compile time</strong>: the following lines are upstream jq&#x27;s diagnostic, which this harness records but never compares. Reproducing jq&#x27;s exact error text is reverse-engineering a C implementation, not conforming to a specification, so a <code>%%FAIL</code> case passes on exit <code>3</code> alone.</p>
<p>Values are compared structurally, not textually. <code>1</code> and <code>1.0</code> are the same jq value; so are two objects whose keys are printed in a different order. Formatting of output is therefore not under test, but the <strong>number and order</strong> of values is.</p>
<h2>Declared exclusions</h2>
<p><code>sources/exclusions.txt</code> names the corpus cases this kit cannot run, with the reason. They are the module-loader cases: <code>import</code> and <code>include</code> resolved against a search path of fixture files that this kit&#x27;s flat source import cannot carry. They are reported as <code>skipped</code> and are not part of the score.</p>
<p>The module <em>grammar</em> cases are <strong>not</strong> excluded and must pass. <code>module (.+1); 0</code>, <code>module []; 0</code>, <code>include &quot;a&quot; (.+1); 0</code>, <code>include &quot;a&quot; []; 0</code>, <code>include &quot;\ &quot;; 0</code>, <code>include &quot;\(a)&quot;; 0</code>, and <code>%::wat</code> are all <code>%%FAIL</code> cases: the front end must parse the module syntax far enough to reject them, without ever touching the filesystem.</p>

<p>What each staged file is for:</p>
<ul><li><code>sources/jq-manual.txt</code> — the jq language manual at 1.8.2, rendered to plain text. The</li></ul>
<p>primary specification, and the normative description of every builtin.</p>
<ul><li><code>sources/jq.test</code> — the conformance corpus. Also the most precise available statement of</li></ul>

<ul><li><code>sources/parser.y</code> — upstream&#x27;s yacc grammar. The authority on operator precedence,</li></ul>

<ul><li><code>sources/lexer.l</code> — upstream&#x27;s lexer. The authority on tokens, string interpolation, and</li></ul>

<ul><li><code>sources/builtin.jq</code> — the subset of jq&#x27;s builtins that upstream defines in jq itself.</li></ul>
<p>Read it as a specification of those builtins&#x27; semantics.</p>
<ul><li><code>sources/run_conformance.py</code>, <code>sources/full_test.sh</code>, <code>sources/exclusions.txt</code> — the</li></ul>
<p>scoring instruments, read-only as stated above.</p>
<h2>Suggested implementation order</h2>
<p>The difficulty is concentrated in one place — the evaluation model — and not spread evenly across the corpus. Build the core correctly before reaching for coverage.</p>
<ol><li><strong>Lexer and parser.</strong> Follow <code>sources/lexer.l</code> and <code>sources/parser.y</code> directly. Produce</li></ol>
<p>an AST. Precedence, <code>?</code> suffixes, string interpolation, and the <code>def</code> forms are all settled there. Reject invalid programs with exit <code>3</code>.</p>
<ol><li><strong>The generator core.</strong> Evaluate a filter as something that yields a stream of values:</li></ol>
<p><code>.</code>, literals, <code>|</code>, <code>,</code>, field access, iteration, arithmetic, comparison, and <code>empty</code>. Every later feature is expressed in terms of this. Get <code>[.[] | f]</code>, cartesian products over multi-output arguments, and short-circuiting right.</p>
<ol><li><strong>Paths and assignment.</strong> <code>path(f)</code>, <code>getpath</code>, <code>setpath</code>, <code>delpaths</code>, <code>del</code>, and then</li></ol>
<p><code>=</code>, <code>|=</code>, <code>+=</code>, and friends. Assignment is defined over path expressions, so this cannot precede step 2.</p>
<ol><li><strong>Control flow.</strong> <code>if</code>/<code>then</code>/<code>elif</code>/<code>else</code>/<code>end</code>, <code>try</code>/<code>catch</code> and <code>?</code>, <code>//</code>,</li></ol>
<p><code>reduce</code>, <code>foreach</code>, <code>label</code>/<code>break</code>, <code>limit</code>, <code>first</code>, <code>last</code>, <code>until</code>, <code>while</code>, <code>recurse</code>. This is where backtracking is tested hardest.</p>
<ol><li><strong>Functions, variables, and destructuring.</strong> <code>def</code> with arity and closures, <code>as</code></li></ol>
<p>bindings, object and array patterns, and the <code>?//</code> alternative operator.</p>
<ol><li><strong>Builtins.</strong> Work outward from <code>sources/builtin.jq</code> and the manual: strings, arrays,</li></ol>
<p>objects, <code>sort_by</code>/<code>group_by</code>/<code>unique_by</code>, <code>@base64</code>/<code>@uri</code>/<code>@csv</code>/<code>@tsv</code>/<code>@sh</code> formats, the date functions, <code>tostream</code>, <code>input</code>/<code>inputs</code>, <code>$__loc__</code>, <code>debug</code>.</p>
<ol><li><strong>Numbers and edge cases.</strong> <code>nan</code>, <code>infinite</code>, integer/float equality, large literals,</li></ol>
<p>and the <code>have_decnum</code> builtin — return <code>false</code> from it and the corpus takes its non-decNumber branch, which native floats satisfy.</p>
<p>The manual is normative and the corpus is precise. Follow both directly rather than inferring behaviour from jq&#x27;s printed output.</p>
<h2>Definition of Done</h2>
<ul><li><code>sh sources/full_test.sh</code> runs cleanly with zero errors and exits zero.</li><li>The program satisfies the <code>./jq -c</code> → stdin → one-JSON-value-per-line → exit-code</li></ul>
<p>contract.</p>
<ul><li>Every corpus case that runs passes: the failed and errored counts are both zero, and the</li></ul>
<p>skipped count matches the declared exclusions. The harness exit status is the verdict and the whole verdict — assert <code>returncode == 0</code> and stop there. Do not assert on the text of the summary line at all: the case totals belong to the pinned corpus, and a check that reads a runner&#x27;s printed output is measuring the runner rather than the interpreter.</p>
<ul><li>Do not create acceptance checks asserting that imported or staged files merely exist.</li><li>The interpreter is written from the specification. **Every third-party jq</li></ul>
<p>implementation or binding is forbidden** — <code>jq.py</code>, <code>pyjq</code>, <code>jqlang</code>, <code>gojq</code>, <code>jaq</code>, and any other — as is shelling out to a system <code>jq</code> binary. A wrapper around real jq scores perfectly and makes the exercise meaningless.</p>
<ul><li>The project declares no third-party runtime dependency. The standard library is</li></ul>
<p>sufficient: <code>json</code>, <code>decimal</code>, <code>math</code>, <code>re</code>, <code>datetime</code>, <code>time</code>, <code>base64</code>, <code>unicodedata</code>, <code>itertools</code>, <code>functools</code>, <code>dataclasses</code>, <code>argparse</code>, <code>sys</code>.</p>
<ul><li>No network access at any point, including at test time. No package is installed, and no</li></ul>
<p>tool beyond <code>python3</code> and POSIX <code>sh</code> is invoked.</p>
<ul><li>Deliver a concise project <code>README.md</code> documenting the stdin/stdout interface, the exit</li></ul>
<p>codes, and the <code>sh sources/full_test.sh</code> command.</p></article>
